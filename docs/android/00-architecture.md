# Android Build — Architecture & Foundation

**Status:** Phase 0/1 planning document. Nothing described here is built yet — no Capacitor
dependency is installed, no `android/` directory exists, no entitlement/billing code exists.
This is the design that subsequent build phases implement against.

**Scope of this document:** the shared substrate every Android app (Tasks, Calendar, Records,
Lists, Notes, Portfolio, Fitness) sits on — process model, multi-entry-point launcher icons,
mobile layout system, native polish, notifications, and monetization/entitlements. It does
**not** contain the per-app Android UX spec (exact screens, gestures, layout for Tasks vs.
Calendar vs. Records) — those are separate, later documents in this same `docs/android/`
folder, written once this foundation is confirmed. See §11 for the full roadmap.

## 1. Vision recap (Android-specific)

The desktop/web suite already ships as one binary containing every app, gated by
`isAppEnabled()` (currently a stub that always returns `true`). Android is the first platform
where that gate becomes real: **Tasks, Calendar, Records, and Lists ship free, bundled
together as "the suite." Notes, Portfolio, and Fitness are individually purchasable
one-time add-ons.** The free tier carries ads; a separate one-time purchase removes them.

Critically, **this is still one Android app — one APK, one Google Play Store listing, one
installed package, one running process** — not a suite of separate apps that happen to share
code. What the user experiences as "installing Notes" is an in-app purchase that unlocks
already-shipped code and reveals a new home-screen icon; nothing is downloaded separately.
This preserves everything the desktop architecture already guarantees for free: Purposes tag
across every app, the in-process event bus fires everywhere, and a single Supabase session
covers the whole suite — because it is, mechanically, still a single running app. See §4 for
exactly how "one icon per app, but one app" is achieved on Android; it is a genuinely
well-supported native pattern (`activity-alias`), not a hack.

## 2. Confirmed Architecture Decisions

These are decided. A future agent should treat re-litigating any of these as requiring an
explicit new instruction from the user, not something to second-guess mid-build.

### ADR-1 — Vehicle: Capacitor, wrapping the existing web codebase

The Android app is the *same* Vite/React/TypeScript/Zustand/CSS-Modules codebase that already
builds the PWA (Vercel) and the desktop app (Tauri) — compiled once more into a native Android
shell via `@capacitor/android`. No component is rewritten, no store is reimplemented, no entity
type changes shape. Capacitor's role is exclusively: (a) host the built `dist/` output in a
native WebView, (b) bridge a small number of native capabilities (notifications, billing, the
multi-entry-point mechanism in §4) into JS via plugins, (c) produce a signed `.aab` for the Play
Store. Business logic never becomes platform-aware beyond reading a `usePlatform()` flag; stores
themselves stay platform-agnostic (see BACKLOG.md §6f's existing rule: never import a
notification/platform service inside a Zustand store).

**Why not React Native / Flutter / a native rewrite:** would mean re-deriving the entire type
system, every store, every component, and the Supabase sync layer a second time, in a second
language/framework, forever kept in sync by hand with the desktop version by hand. Capacitor
costs a thin platform-detection layer and a handful of native plugins; the alternative costs a
parallel product built from scratch. Given the stated workflow ("desktop first, Android
follows"), Capacitor is the only option where that workflow doesn't mean double-building every
feature forever.

**Why not Tauri's own Android target:** Tauri v2 does have a native Android build path, and
`tauri.conf.json` has a vestigial stub from it (see §0). It was not pursued and should not be —
picking it *now* would mean maintaining two parallel native-shell toolchains (Tauri for
desktop, Tauri-mobile *or* Capacitor for Android) for no benefit, since Capacitor already covers
the Android need on top of the exact same web build Tauri's desktop shell also consumes.
Capacitor is more mature specifically for Android production shipping (docs, plugin ecosystem,
Play Store precedent) and is what BACKLOG.md's prior planning pass already committed to in
detail — don't reopen this.

### ADR-2 — One app, one listing

Single `.aab`, single Play Store listing, single `applicationId`. Every app in the suite (free
or paid) ships inside that one package from day one — "buying" Notes/Portfolio/Fitness does not
trigger any download; it flips an entitlement flag already checked by code already present in
the installed APK. This is what makes cross-app integration (Purposes, event bus, shared auth
session) work identically to desktop with zero extra plumbing: there is only ever one process.

### ADR-3 — Multi-entry-point launcher icons, on top of one app

The user wants a distinct home-screen icon per app/section (Tasks, Calendar, Records, Lists,
and — once purchased — Notes, Portfolio, Fitness), the way separate apps would look, *without*
paying the cost of actually being separate apps. Android supports this natively via
`activity-alias`: multiple launcher-visible icons, each independently labelled and iconed, all
resolving to the same single `MainActivity`/process/storage. Tapping any icon opens the one
running app, pre-routed to that entry point's section. Full mechanics in §4. This requires one
small custom native plugin (Capacitor doesn't ship this out of the box) — scoped and specified
in §4, not large.

Free-tier entry points (Tasks, Calendar, Records, Lists) are always enabled. Paid entry points
(Notes, Portfolio, Fitness) are disabled at install time and enabled at runtime the moment their
purchase is confirmed — see §7.

### ADR-4 — Monetization model

- **Tasks, Calendar, Records, Lists** — free, bundled, always installed, never gated. Carries
  ads (banner, placement detailed in §7c) inside these four apps only.
- **Notes** — free for now, alongside the four above. **Corrected from this document's first
  draft**, which classified Notes as a paid add-on — that directly contradicted the shipped
  desktop code (`src/config/apps.ts`'s `APP_TIERS.notes` is `'core'`, and Notes is bundled/free
  on desktop today), a contradiction an audit of this document set caught. Decided: keep Notes
  free, but built so it can become a paid add-on later via a one-line config change, not an
  architecture change — see the `ANDROID_PAID_APPS` mechanism in ADR-5 and §7a below. Nothing
  about Notes' entry point, nav visibility, or ad-free status depends on this file being edited
  again if that toggle flips later.
- **Portfolio, Fitness** — each an individual one-time (non-subscription) in-app purchase via
  Google Play Billing, matching `APP_TIERS`'s existing `'addon'` classification for both on
  desktop. Owning one has no bearing on the other. Neither ever shows ads, regardless of the
  free tier's ad state — paid, so ad-free by construction, not by a separate check. (If Notes is
  ever flipped to paid per the above, it inherits this same ad-free-when-owned rule
  automatically — nothing extra to build for that case either.)
- **"Remove Ads"** — a separate one-time purchase. Removes ads from the free tier (Tasks/
  Calendar/Records/Lists/Notes) for a user who wants a clean free experience without buying any
  add-on. Independent of add-on ownership in both directions: owning an add-on does not imply
  ads are removed from the free tier, and buying "Remove Ads" does not unlock any add-on.
- All purchases are one-time (`inapp` product type in Play Billing terms), not subscriptions.
  Nothing in this plan should introduce recurring billing.

### ADR-5 — Entitlement checking reuses the existing `isAppEnabled()` seam, gated by its own list — not `APP_TIERS`

`src/config/apps.ts`'s `isAppEnabled(view)` already exists as the single gating point the
desktop build calls at three sites (`NavSidebar`, `App.tsx`'s section routing, the `6`/`7` nav
hotkeys) — today it's a stub that always returns `true`.

**Corrected from this document's first draft**, which had `isAppEnabled()` branch on
`APP_TIERS[view] === 'core'`. That's wrong on two counts, both caught by an audit of this
document set: (1) `APP_TIERS.notes` is `'core'` today, so that check would return `true` for
Notes *unconditionally*, before ever consulting purchase state — even if Notes were classified
as a paid Android add-on elsewhere in this plan, this implementation would silently never
enforce it; (2) `APP_TIERS` governs desktop's nav grouping (which section shows above/below the
`<hr>` divider) — a completely different concern from "which apps require an Android purchase,"
and conflating the two is exactly what ADR-4's "flip Notes to paid later with a one-line change"
goal needs to avoid.

**Fix: a new, Android-only, standalone list is the single source of truth for monetization
tier**, decoupled from `APP_TIERS` entirely:

```typescript
// src/config/androidMonetization.ts
// The ONLY place that decides which apps require an Android purchase. Unrelated to APP_TIERS
// (which governs desktop nav grouping, a different concern). To make an app paid later —
// including Notes, see ADR-4 — add its AppView here. Nothing else needs to change: the
// EntitlementStore (§7a) is keyed generically, isAppEnabled() below reads this list generically,
// and the entry-point enable/disable (§4.5) already keys off entitlement state, not this list
// directly, so it needs no change either.
export const ANDROID_PAID_APPS: ReadonlySet<AppView> = new Set(['portfolio', 'fitness']);
// (Notes stays out of this set for now, per ADR-4 — add 'notes' here when/if that changes.)
```

```typescript
// src/config/apps.ts
import { Capacitor } from '@capacitor/core';
import { ANDROID_PAID_APPS } from './androidMonetization';
import { useEntitlementStore } from '@/store/entitlementStore';

export function isAppEnabled(view: AppView): boolean {
  if (Capacitor.getPlatform() !== 'android') return true;   // desktop/web: never gated
  if (!ANDROID_PAID_APPS.has(view)) return true;             // free on Android — independent of APP_TIERS
  return useEntitlementStore.getState().isOwned(view);
}

// Reactive variant — REQUIRED at render-time call sites (NavSidebar, App.tsx's section-routing
// JSX). The plain function above reads a non-reactive store snapshot: calling it inside render
// with no subscription means a purchase completing, or entitlements hydrating from Supabase on
// launch, won't trigger a re-render at all — the newly-bought app's nav entry would silently
// stay hidden until something unrelated happened to re-render that component. This was caught
// by the same audit and is a real bug class ("works in manual testing where you also happen to
// interact with the screen right after purchase, silently stale otherwise"), not a style
// preference.
export function useIsAppEnabled(view: AppView): boolean {
  const platform = Capacitor.getPlatform();
  const owned = useEntitlementStore((s) => s.isOwned(view)); // real subscription
  if (platform !== 'android') return true;
  if (!ANDROID_PAID_APPS.has(view)) return true;
  return owned;
}
```

**Which call sites need which variant:** `NavSidebar` and `App.tsx`'s section-routing JSX
(`{activeView === 'fitness' && isAppEnabled('fitness') && ...}`) both evaluate during render and
**must** switch to `useIsAppEnabled(view)`. The `6`/`7` nav hotkey handler runs inside a
`keydown` event callback, not render — a fresh non-reactive read via the plain `isAppEnabled()`
function is correct there (there's nothing to subscribe to; it just needs the current value at
the moment of the keypress). This is a small but real correction to the file manifest (§9) —
two of the three existing call sites need a one-line hook swap, not zero changes as originally
claimed.

> **Decided (see §13):** because desktop/PWA never paywall anything, a user could get Notes/
> Portfolio/Fitness for free simply by opening the PWA in their phone's browser instead of
> installing the Android app — the exact same build, unlocked. Confirmed as an accepted
> tradeoff, not a gap to close: leave desktop/PWA exactly as they are, no gating, no second
> payment provider. Revisit only if real usage data ever suggests this is actually costing
> meaningful revenue.

### ADR-8 — What's actually shared is the data layer, not the UI

**Revises this document's original framing of §5b — read this before writing any per-app
Android UX spec.** Capacitor's only job is running a web app in a native shell with plugin
access to device APIs; it has no opinion on what gets rendered inside that shell. The first
draft of this document defaulted to the cheapest possible interpretation — reuse desktop's
existing components verbatim, adapt them with responsive CSS (full-screen panes, hidden
sidebars, bottom sheets). That's a reasonable *fallback* for screens where desktop's layout
already degrades acceptably at phone widths and the interaction is inherently
occasional/complex (building a tracker's field schema, deep Portfolio chart configuration). It
is **not** the right default for the screens mobile users touch constantly — quick-adding a
task, adding a calendar item, logging a routine, capturing a photo. Those get **new,
purpose-built mobile components**, not resized desktop ones.

**What's actually shared, unconditionally, regardless of which UI renders it:** every Zustand
store and its actions, every entity type, the Supabase sync layer, validation/computed-value
logic, utils (`date.ts`, `timeGrid.ts`, etc.), and the shared platform layer (Purposes, event
bus, auth). A new mobile-only component calling `taskStore.addTask()` is exactly as "shared" as
desktop's `AddTaskModal` calling the same action — the sharing happens one layer down from the
component tree, not at the component tree itself. This is *why* Capacitor (or any web-tech
vehicle) is worth it even when the UI diverges substantially: duplicating a fast quick-add
component costs a few hundred lines; duplicating task validation, deadline/scheduled-date
sync-to-calendar logic, Supabase conflict resolution, and every entity type would cost far more
and drift out of sync over time. **The vehicle question and the "how much UI do we share"
question are independent** — this plan answers the first (Capacitor) without presupposing an
answer to the second, which is now decided per-screen, not wholesale, in each per-app document.

**Native-only capabilities are a first-class category, not an edge case.** Camera/photo capture
(`@capacitor/camera`), and other device APIs that make sense later (share sheet, contacts,
biometric unlock) are exactly the kind of thing that justifies Capacitor over a bare PWA — a
plugin call from otherwise-ordinary React code, no native rewrite required. When a per-app
document identifies a feature that only makes sense with a device capability (e.g. attaching a
photo to a task or note), spec it as: a small new mobile-only component + the relevant Capacitor
plugin + a call into the existing store's existing update action. Don't invent a parallel data
path for "mobile-captured" content — it's the same `Task`/`Note` entity, same store, same sync.

**What this changes about the rest of this document:** §5b's carried-forward BACKLOG.md layout
notes (full-screen panes, hidden sidebars) still apply to the screens where they're the right
call — but each future per-app document (`01-tasks-app.md`, `02-calendar-app.md`, etc.) must
explicitly decide, screen by screen, "reuse desktop's component responsively" vs. "build a new
mobile-specific component," rather than assuming the former everywhere. Expect the answer to
lean toward new components for anything in the daily-use hot path, and toward reuse for
occasional/configuration-heavy screens — matching the "mobile is optimised for consumption,
quick-capture, and daily logging; desktop ships more advanced configuration UX" principle
BACKLOG.md already stated but didn't fully follow through on in its layout section.

### ADR-9 — Migrations must stay backward-compatible across an Android release lag

**A standing rule, not a one-time task.** The stated workflow is "build on desktop first,
Android follows" — but Android releases go through Play Store review (hours to days, sometimes
longer for the very first submission) while desktop/PWA deploy instantly via Vercel/direct
distribution. That gap means an Android user can be running client code that's meaningfully
older than what desktop is currently talking to in Supabase, for longer than any web/desktop
user ever would be. If a Supabase migration or a Zustand store version bump ever became a
*breaking* change (renaming/removing a column, changing a field's meaning), an out-of-date
Android install would break for real users with no way to force-update.

The project's existing migration discipline already avoids this by accident — every migration
in `supabase/migrations/` to date is purely additive (new nullable columns with defaults), and
the Zustand migration rule (cumulative `migrate` functions backfilling defaults) is inherently
tolerant of older clients ignoring fields they don't know about yet. **This ADR makes that
existing discipline an explicit, permanent requirement once Android ships**, not just an
incidental pattern: no Supabase migration may rename or remove a column or change a column's
semantic meaning without a compatibility window; no store version bump may require that older
clients be unable to read newer data. This costs nothing when followed (it's what's already
happening) but is worth stating outright so a future migration doesn't casually break it once
there's a slower-moving Android install base depending on it.

## 3. Terminology addition

One new term for the Android-specific vocabulary, added here rather than CLAUDE.md's main
terminology table since it's Android-only:

| Term | Meaning |
|------|---------|
| **Entry point** | A distinct home-screen/app-drawer icon that launches the single installed app directly into one section or app (e.g. the Tasks entry point, the Calendar entry point). Implemented as an `activity-alias` (§4). Not a separate app, not a separate process — a launch route into the one app. |
| **Entitlement** | A boolean record of whether the current user has purchased a given add-on (`notes`, `portfolio`, `fitness`) or ad removal (`adsRemoved`). Stored in `entitlementStore`, mirrored to Supabase for cross-device consistency (§7a). |

## 4. Multi-entry-point launcher icons — full technical spec

This is the single most novel piece of native work in the whole Android build, so it gets full
mechanical detail rather than a sketch. Everything below happens in the native
`android/app/src/main/` tree that `npx cap add android` generates (a real Android/Kotlin
project, committed to git per BACKLOG.md §1's existing instruction) plus one small custom
Capacitor plugin.

**Not a blocker for per-app UI work.** This mechanism changes how the app is *launched*, not
how any individual app/section is *built* — `01-tasks-app.md`, `02-calendar-app.md`, etc. can be
built and fully tested using Capacitor's default single launcher icon (whatever `cap add
android` generates out of the box) before this section is implemented at all. Build this
whenever convenient — in parallel with per-app work, or after — not as a hard gate on Track A
step 7 (§10).

### 4.1 Which entry points exist

Seven possible entry points, matching the suite's Section/App levels (deliberately not strictly
one-per-"App" in the CLAUDE.md terminology sense — Tasks/Calendar/Records/Lists are each
Organizer *sections*, but the user explicitly wants each as its own icon, so entry points are
granted at whichever level people actually want quick access to):

| Entry point key | Section/App it opens | Tier | Enabled by default |
|---|---|---|---|
| `tasks` | Tasks (Organizer) | Free | Yes |
| `calendar` | Calendar (Organizer) | Free | Yes |
| `records` | Records (Organizer) | Free | Yes |
| `lists` | Lists (Organizer) | Free | Yes |
| `notes` | Notes (app) | Free (see ADR-4) | Yes |
| `portfolio` | Portfolio (app) | Paid add-on | No — enabled on purchase |
| `fitness` | Fitness (app) | Paid add-on | No — enabled on purchase |

Tier column is driven entirely by `ANDROID_PAID_APPS` (ADR-5) — an entry point is enabled by
default unless its key is in that set. If Notes is ever added to `ANDROID_PAID_APPS`, its row
here flips to "No — enabled on purchase" with no other change to this table's structure.

Each maps 1:1 to an `AppView` value already defined in `src/types/index.ts` — no new type is
needed, `EntryPointKey` (a new small union in the Android-specific code, e.g.
`src/services/android/entryPoints.ts`) is just `AppView` restricted to these seven values.

### 4.2 AndroidManifest.xml structure

Capacitor generates one real `<activity>` — `MainActivity` (extends `BridgeActivity`), the sole
host of the WebView. It gets `android:launchMode="singleTask"` (critical — see §4.4) and, for
the free tier, does **not** itself carry a `LAUNCHER` intent-filter; instead, every entry point
including the "default" one a user gets on first install is its own `activity-alias`. This keeps
all seven treated uniformly rather than special-casing one as "the real launcher and six
aliases."

```xml
<application ...>
    <activity
        android:name=".MainActivity"
        android:exported="false"
        android:launchMode="singleTask"
        android:configChanges="orientation|keyboardHidden|keyboard|screenSize|locale|smallestScreenSize|screenLayout|uiMode"
        android:theme="@style/AppTheme.NoActionBarLaunch">
        <!-- no intent-filter here — only aliases are launcher-visible -->
    </activity>

    <activity-alias
        android:name=".entry.TasksEntry"
        android:targetActivity=".MainActivity"
        android:enabled="true"
        android:exported="true"
        android:icon="@mipmap/ic_entry_tasks"
        android:label="@string/entry_tasks_label">
        <intent-filter>
            <action android:name="android.intent.action.MAIN" />
            <category android:name="android.intent.category.LAUNCHER" />
        </intent-filter>
    </activity-alias>

    <activity-alias
        android:name=".entry.CalendarEntry"
        android:targetActivity=".MainActivity"
        android:enabled="true"
        android:exported="true"
        android:icon="@mipmap/ic_entry_calendar"
        android:label="@string/entry_calendar_label">
        <intent-filter>
            <action android:name="android.intent.action.MAIN" />
            <category android:name="android.intent.category.LAUNCHER" />
        </intent-filter>
    </activity-alias>

    <!-- .entry.RecordsEntry, .entry.ListsEntry — identical shape, android:enabled="true" -->

    <activity-alias
        android:name=".entry.NotesEntry"
        android:targetActivity=".MainActivity"
        android:enabled="false"
        android:exported="true"
        android:icon="@mipmap/ic_entry_notes"
        android:label="@string/entry_notes_label">
        <intent-filter>
            <action android:name="android.intent.action.MAIN" />
            <category android:name="android.intent.category.LAUNCHER" />
        </intent-filter>
    </activity-alias>

    <!-- .entry.PortfolioEntry, .entry.FitnessEntry — identical shape, android:enabled="false" -->
</application>
```

Note the paid entry points start `android:enabled="false"` — their icon simply does not appear
on the home screen/app drawer until enabled at runtime (§4.3). This is the actual gating
mechanism for "installable add-ons that show up as their own icon once bought" — nothing to do
with `isAppEnabled()` server-side, that's a separate in-app nav gate (ADR-5); this is the
launcher-icon-visibility gate specifically.

Every alias needs its own launcher icon asset (`@mipmap/ic_entry_*`, adaptive icon XML +
foreground/background layers per standard Android icon guidelines) and its own label string in
`res/values/strings.xml`. Design requirement, not just plumbing: seven visually related icon
marks (same base brand mark, distinguished by per-app colour/glyph — mirrors the icon-per-nav-
item scheme `NavSidebar` already uses on desktop) need to be produced before this ships. Flag
this to design/asset work early; it blocks the whole feature otherwise.

### 4.3 The custom native plugin (`EntryPointPlugin`)

Nothing above is exposed to JS by any stock Capacitor plugin. One small custom plugin is
required — a single Kotlin class, following Capacitor's documented "create a plugin" pattern
(`@CapacitorPlugin`-annotated class with `@PluginMethod` functions), registered in
`MainActivity`'s plugin list.

```kotlin
// android/app/src/main/java/com/organisaitor/app/EntryPointPlugin.kt
@CapacitorPlugin(name = "EntryPoint")
class EntryPointPlugin : Plugin() {

    // Reads which alias launched (or re-launched, via onNewIntent) the activity.
    // The trick: an Intent delivered via an activity-alias reports the ALIAS's own
    // component name from intent.component, not the target activity's — this is
    // standard, documented Android behaviour and the whole mechanism this relies on.
    @PluginMethod
    fun getLaunchSection(call: PluginCall) {
        val section = resolveSectionFromIntent(activity.intent)
        val ret = JSObject()
        ret.put("section", section) // one of the EntryPointKey strings, or null
        call.resolve(ret)
    }

    // Called from JS after a purchase is confirmed (or refunded) to show/hide that
    // entry point's launcher icon. `enabled=false` on a currently-owned entry point
    // is only relevant if a refund path is ever built — not expected in normal use.
    @PluginMethod
    fun setEntryEnabled(call: PluginCall) {
        val section = call.getString("section") ?: return call.reject("section required")
        val enabled = call.getBoolean("enabled") ?: return call.reject("enabled required")
        val componentName = ComponentName(context, aliasClassNameFor(section))
        context.packageManager.setComponentEnabledSetting(
            componentName,
            if (enabled) PackageManager.COMPONENT_ENABLED_STATE_ENABLED
                        else PackageManager.COMPONENT_ENABLED_STATE_DISABLED,
            PackageManager.DONT_KILL_APP
        )
        call.resolve()
    }

    private fun resolveSectionFromIntent(intent: Intent?): String? {
        val className = intent?.component?.className ?: return null
        return when {
            className.endsWith("TasksEntry")     -> "tasks"
            className.endsWith("CalendarEntry")  -> "calendar"
            className.endsWith("RecordsEntry")   -> "records"
            className.endsWith("ListsEntry")     -> "lists"
            className.endsWith("NotesEntry")     -> "notes"
            className.endsWith("PortfolioEntry") -> "portfolio"
            className.endsWith("FitnessEntry")   -> "fitness"
            else -> null
        }
    }

    private fun aliasClassNameFor(section: String): String =
        "com.organisaitor.app.entry.${section.replaceFirstChar { it.uppercase() }}Entry"
}
```

JS-side wrapper (`src/services/android/entryPoint.ts`), following the existing pattern of
Capacitor-aware service wrappers already used for notifications:

```typescript
import { registerPlugin } from '@capacitor/core';

interface EntryPointPlugin {
  getLaunchSection(): Promise<{ section: string | null }>;
  setEntryEnabled(opts: { section: string; enabled: boolean }): Promise<void>;
}

const EntryPoint = registerPlugin<EntryPointPlugin>('EntryPoint');

export async function getLaunchSection(): Promise<AppView | null> {
  if (!Capacitor.isNativePlatform()) return null;
  const { section } = await EntryPoint.getLaunchSection();
  return section as AppView | null;
}

export async function setEntryPointEnabled(section: AppView, enabled: boolean): Promise<void> {
  if (!Capacitor.isNativePlatform()) return;
  await EntryPoint.setEntryEnabled({ section, enabled });
}
```

### 4.4 Launch routing in App.tsx

Two moments matter: cold start (app wasn't running) and warm re-entry (app was already running
in the background and a *different* entry-point icon was tapped).

**Cold start:** before the first meaningful render (after stores hydrate from localStorage —
same timing as the existing dark-mode FOUC-prevention concern), call `getLaunchSection()` and,
if non-null, call `setActiveView(section)` before the user sees anything else. This is a small
addition to the existing app-mount effect chain, not a new architectural layer.

**Warm re-entry (`onNewIntent`):** because `MainActivity` is `launchMode="singleTask"`, tapping
a second entry-point icon while the app is already running does **not** spin up a second
instance — Android delivers a fresh `Intent` to the existing activity's `onNewIntent`, which
must call `setIntent(intent)` (so `activity.intent` reflects the new one) and notify JS. Extend
`EntryPointPlugin` with a Capacitor plugin event:

```kotlin
override fun handleOnNewIntent(intent: Intent) {
    super.handleOnNewIntent(intent)
    val section = resolveSectionFromIntent(intent)
    if (section != null) {
        val data = JSObject()
        data.put("section", section)
        notifyListeners("sectionRequested", data)
    }
}
```

JS side subscribes once in `App.tsx` (Android-gated), mirroring the existing `appUrlOpen`
deep-link listener pattern from BACKLOG.md §6g:

```typescript
useEffect(() => {
  if (!isAndroid) return;
  const handle = EntryPoint.addListener('sectionRequested', ({ section }) => {
    if (section) setActiveView(section as AppView);
  });
  return () => { handle.then(l => l.remove()); };
}, [isAndroid]);
```

### 4.5 Entitlement-driven enable/disable

`entitlementStore` (§7a) calls `setEntryPointEnabled(view, true)` the moment a purchase is
confirmed, and on every app launch reconciles every entry point listed in `ANDROID_PAID_APPS`
(ADR-5) against current entitlement state (covers the case where a purchase was made on a fresh
install that hasn't run the reconciliation yet). This reconciliation is a single small effect
iterating that set, not a recurring background task — and it automatically covers Notes too if
that's ever added to the set, with no change needed here.

**Known platform quirk to document, not "fix":** some OEM launchers cache their icon list and
may not visually refresh an enabled/disabled icon until the user reopens the app drawer or
occasionally re-boots the launcher. This is a general Android limitation with
`setComponentEnabledSetting`, not a bug in this implementation — don't spend time trying to
force a refresh beyond what the API provides.

### 4.6 Play Store policy note

This is one APK/one listing with multiple launcher-visible components — a long-standing,
policy-safe Android pattern (used by icon-pack apps, multi-mode utility apps, etc.), not
multiple apps in disguise. Worth a quick policy-page re-check at implementation time since store
policy specifics do shift, but there is no structural reason this would be flagged.

### 5b. Mobile layout system

**Read ADR-8 before this section — it revises the framing below.** The shell-level pieces
(bottom tab bar, overflow sheet, full-screen panes for slide-in panes generally) are genuinely
shared infrastructure and are carried forward from BACKLOG.md §4 largely as-is. What's **not**

the wrong call for others, decided per-screen in each per-app document (§11), not assumed here.

Shell-level pieces, largely carried forward from BACKLOG.md §4 — **except the tab list, see the
correction immediately below**:
- `MobileNav` — bottom tab bar for moving between sections once already inside the app.
- `MobileMoreSheet` — bottom sheet for nav items that don't fit the tab bar.
- Full-screen slide-in panes on mobile (detail panes like TaskPane, NoteEditorPane, etc.).
- Android back-button handling — see §5d for the actual (corrected) mechanism; not restated here
  to avoid two descriptions of the same thing drifting apart.

**`MobileNav`'s tab list, corrected.** BACKLOG.md's original spec hardcoded five tabs — Tasks,
Calendar, Records, **Notes**, More — written before Lists existed as a section and before this
document's tier decisions. Every per-app document (01–04) independently states "`MobileNav`
includes a [Tasks/Calendar/Records/Lists] tab," which only holds if the tab list is actually
updated here; an audit of this document set caught that it never was. **Corrected tab list:
Tasks, Calendar, Records, Lists, More** — the four Organizer *sections* (matching the entry-point
table's own Organizer-section grouping, §4.1) get tabs; Notes, Portfolio (once owned), and
Fitness (once owned) live in `MobileMoreSheet` alongside Settings/Account, regardless of any of
their tiers. This deliberately decouples the tab bar from monetization status entirely — Notes
moving between free and paid (ADR-4) never requires touching `MobileNav`, since it was never in
the tab bar to begin with, only ever in the More sheet.

Deltas since BACKLOG.md §4 was written:

- **The bottom tab bar and the multi-entry-point icons are complementary, not redundant.**
  Entry points get you *into* the app at a specific section from the home screen; the bottom tab
  bar lets you move *between* sections once already inside, without backing out to the home
  screen. Keep both.
- **Per ADR-8, the highest-frequency creation flows get new mobile-specific components, not a
  resized `AddTaskModal`/`AddCalendarItemModal`.** Each per-app document decides exactly which
  screens this applies to (expect: quick-add for tasks, quick-add for calendar events/reminders,
  routine step logging) versus which screens are fine reused responsively (expect: detail/edit
  panes for an already-created item, list views, settings). This is a per-app-document decision,
  not something resolved wholesale here.
- **Fitness needs a section-specific layout note added** (BACKLOG's existing per-section notes
  predate Fitness): activity list is already a simple vertical list (no layout change needed);
  `AddActivityModal`'s type-pill row and field editor should follow the same bottom-sheet-on-
  mobile pattern every other creation modal already uses, *or* be replaced with a faster mobile
  log-flow per ADR-8 if daily-logging frequency justifies it — decide in that app's own document.
- **Schedule (a Calendar sub-feature) needs a mobile note**: `ManageSchedulesPane` and
  `AddScheduleModal`'s block editor (including the click-to-add-block grid, §-referenced in
  CLAUDE.md) are inherently wide, desktop-oriented tools. On Android, both should remain
  reachable but are explicitly **not layout-optimised for phase 1** — same "accessible but not
  optimised" carve-out BACKLOG.md already grants tracker field-schema building and Portfolio's
  chart deep-dive. Revisit only if real usage data says otherwise.

### 5c. Dark mode / Android default theme

Desktop's dark mode is already fully implemented (`src/index.css` CSS variables, `data-theme`
attribute, FOUC-prevention script, `settingsStore.theme`) — this is *not* rebuilt for Android,
it's reused as-is. The one Android-specific delta, already decided in BACKLOG.md §Dark Mode line
1348 and still correct: **Android's default theme is `'dark'`, not `'system'`** (every other
platform defaults to `'system'`). Implementation: `settingsStore`'s initial state / migration
picks the default conditionally —

```typescript
import { Capacitor } from '@capacitor/core';
const defaultTheme = Capacitor.getPlatform() === 'android' ? 'dark' : 'system';
```

— bump `settingsStore`'s version and add a migration that backfills `theme: 'system'` for

### 5d. Native polish

Carried forward from BACKLOG.md §5 unchanged: StatusBar theme sync, SplashScreen hide-after-
hydration, haptics wrapper (`src/utils/haptics.ts`) wired to completion-toggle interactions
across Tasks/Records/Lists. Nothing here changes because of monetization or multi-entry-point
work — implement as originally specified.

**Back-button handling — corrected to a single, generic priority model.** BACKLOG.md's original
spec ("closes the topmost open modal/pane via `uiStore` state") only accounts for one kind of
"thing that should intercept back" — a modal/pane boolean. Per-app documents (Records §3, Lists
§2) later added a second, structurally different kind: a master-detail screen's detail→list
navigation, which isn't a modal/pane at all. An audit of this document set correctly flagged
that nothing defines how one global back handler is supposed to know about both kinds, or which
takes priority if a modal happened to be open on top of a detail view. Fixed with one small,
generic mechanism instead of hardcoding every case the global handler has to know about:

```typescript
// src/store/uiStore.ts — addition
mobileBackConsumer: (() => boolean) | null;   // returns true if it handled the back press
registerMobileBackConsumer: (fn: (() => boolean) | null) => void;
```

Any screen that wants "Android back should do something other than the system default" —
today: any master-detail screen's detail view (Records, Lists) — registers itself as the sole
consumer on mount and clears it (`registerMobileBackConsumer(null)`) on unmount:

```typescript
useEffect(() => {
  registerMobileBackConsumer(() => { clearSelection(); return true; });
  return () => registerMobileBackConsumer(null);
}, []);
```

The global Android back-button listener (`@capacitor/app`'s `backButton` event) checks, in
order: (1) is a modal/pane open per existing `uiStore` state — close it, handled; (2) is
`mobileBackConsumer` set — call it, handled if it returns `true`; (3) neither — fall through to
system back/minimize. **Only one master-detail screen is ever visible at a time** (they're
different sections), so a single consumer slot is sufficient — no stack needed unless a future
screen nests two independent collapsible master-detail levels inside one section, which nothing
currently planned does. If that ever happens, upgrade the single slot to a stack at that point,
not preemptively.

**Standing rule, found necessary while fixing this: any collapsible master-detail screen's
selection state must live in `uiStore`, read and written from there — not local component
`useState`.** The `clearSelection()` callback a screen registers above only works if clearing it
actually changes what that screen renders; local state mirrored one-way into `uiStore` (write
without read) breaks this silently, since the store update has nothing left to notify. This
exact mistake was caught in `04-lists-app.md` (see that file's corrected §2/§3) — `ListsSection`
today drives its detail view from local `useState`, one-way-synced *into* `uiStore.activeListId`,
never read back out. Apply this rule to any future master-detail screen (a Notes tree
drill-down, a future Portfolio ticker list+detail) from the start, rather than each one
rediscovering the same bug independently.

**New item, found while speccing Calendar (Phase 2):** `src/utils/links.ts`'s `openExternalLink()`
already branches on Tauri (via `@tauri-apps/plugin-opener`) versus plain browser `window.open()`,
because neither Tauri's nor a bare WebView's default link handling reliably opens external URLs
— this was a real bug fixed for desktop (see CLAUDE.md's "External links now open under Tauri"
entry). **The same problem exists under Capacitor for exactly the same reason** — Android
WebViews don't reliably hand off `target="_blank"`/external navigation either. Add an
Android branch to `openExternalLink()` using `@capacitor/browser`'s `Browser.open({ url })`,
mirroring the existing Tauri branch. This is a shared utility used by every app (Tasks link
pills, Notes hyperlinks, Lists items, Calendar's location-to-Maps link) — fix it once here, not
per-app. Flagged concretely by Calendar's "tap a location to open Maps" feature, but applies
everywhere `openExternalLink()` is already called.

## 7. Monetization & entitlements

### 7a. `entitlementStore` — data model

New Zustand store, Android-only in practice (never mounted/read meaningfully on other
platforms, but not platform-branched in its own definition — it simply always reports "owned"
on non-Android via `isAppEnabled()`'s own platform check, per ADR-5, so this store's contents
never need to be consulted outside Android code paths).

**Generic, keyed shape — not one fixed boolean field per app.** The first draft of this section
used named fields (`notesOwned`, `portfolioOwned`, `fitnessOwned`); redesigned to a generic map
keyed by `AppView` so that adding a new paid app later (including flipping Notes per ADR-4) is
purely a `ANDROID_PAID_APPS` config change (ADR-5) plus a new Play Billing product — zero store
schema changes, zero migration, nothing here to edit:

```typescript
// src/store/entitlementStore.ts
interface EntitlementState {
  owned:          Partial<Record<AppView, boolean>>; // e.g. { portfolio: true } once purchased;
                                                        // an app absent from this map is treated
                                                        // as not-owned, same as explicit `false`
  adsRemoved:     boolean;
  lastSyncedAt:   string | null;   // ISO — last successful Supabase reconcile
  isOwned:        (view: AppView) => boolean;                        // owned[view] ?? false
  setOwned:       (view: AppView, value: boolean) => void;
  setAdsRemoved:  (value: boolean) => void;
  hydrateFromSupabase: () => Promise<void>;
}
```

Persisted to localStorage (`persist` middleware, key `todo-entitlements`) so purchase state
survives app restarts without a network round-trip, *and* mirrored to a new Supabase table
(`user_entitlements`, one row per `user_id`) so a signed-in user's purchases are recoverable if
they reinstall the app or (in principle, though Android is the only mobile platform for now)
sign in elsewhere. Register `todo-entitlements` in `PERSISTED_STORAGE_KEYS`
(`src/config/backup.ts`) per the project's standing rule for new persisted stores.

**Guest mode interaction:** a purchase made in guest mode (no Supabase account) is retained via
the local persisted store but cannot be recovered on reinstall — same limitation guest mode
already has for every other kind of data. Do not build special-case purchase-restore UX for
guests; Play Billing's own "restore purchases" flow (queried from the Play Store account itself,
independent of app-level auth) is the actual safety net here, and should be surfaced as a
"Restore purchases" button in the Account/Settings pane, Android-only.

### 7b. Google Play Billing integration

Integrate via a Capacitor community plugin wrapping Google's Play Billing Library — confirm the
current best-maintained plugin at implementation time (the ecosystem here shifts; do not assume
a specific package name without checking what's actively maintained then). The integration
pattern, regardless of exact plugin chosen:

1. Define one `inapp` (one-time, non-consumable) product per entry in `ANDROID_PAID_APPS`
   (ADR-5) — today that's `add_on_portfolio` and `add_on_fitness` — plus `remove_ads`. If Notes
   is ever added to `ANDROID_PAID_APPS`, add `add_on_notes` here at the same time; nothing else
   in this integration changes shape. Non-consumable is important — these are "own it forever"
   purchases, not something that gets consumed and
   re-buyable.
2. On app launch (and on-demand from a "Restore purchases" action), query owned purchases via
   the billing plugin and reconcile against `entitlementStore` — if Play reports a product as
   owned but the local store doesn't reflect it (fresh install, cleared app data), update the
   store and call `setEntryPointEnabled()` (§4.5) accordingly.
3. Purchase flow: user taps "Buy" in the relevant add-on's locked-state screen (§7d) →
   launch the billing plugin's purchase flow for that SKU → on success callback, update
   `entitlementStore`, enable the entry point, and push the entitlement to Supabase.
4. **Server-side receipt validation** is the correct long-term approach (verifying the purchase
   token against Google's Play Developer API from a small edge function, mirroring the existing
   `api/` pattern used for Strava/ticker proxying) rather than trusting the client-reported
   purchase state outright — flag this as a hardening step to do before wide release, not
   something that blocks an initial internal-testing build. Document it here so it isn't
   silently forgotten: **client-trusted entitlements are acceptable for internal testing only.**

### 7c. AdMob integration

Per ADR-4: ads appear only inside Tasks, Calendar, Records, and Lists, and only when
`entitlementStore.adsRemoved` is `false`. Integrate via a Capacitor community AdMob plugin
(again: confirm current best-maintained option at implementation time). Recommended placement:
a single anchored banner ad, fixed to the bottom of the screen, above the `MobileNav` bottom tab
bar (not overlapping it), shown identically across all four free sections — one ad unit ID
reused across all four rather than four separate placements, to keep this simple and avoid ad
fatigue from multiple simultaneous units. No interstitials in this initial plan — a banner is
far less disruptive to a productivity app's daily-use pattern, and nothing in the user's ask
called for anything heavier; revisit only if real revenue data suggests it's warranted.

The banner component (`src/components/AdBanner/AdBanner.tsx`, Android-only, rendered
conditionally in `App.tsx` alongside `MobileNav`) reads `entitlementStore.adsRemoved` and simply
renders nothing when `true` — no separate "hide ads" code path elsewhere, one component owns
this entirely.

**Consent is a hard requirement, not an enhancement.** Serving any AdMob ad without a consent
flow risks Play Store rejection and GDPR/UK-GDPR non-compliance for EEA/UK users, and Google's
own AdMob terms require it. Before the first ad request, integrate Google's User Messaging
Platform (UMP) SDK (via the same AdMob plugin, which typically bundles UMP support) to show the
consent form where legally required and gate ad loading on the resulting consent state. This is
a fixed step in §10's build order, not an optional polish item — add it as its own numbered step
when this phase is actually implemented.

### 7d. Locked-state screens for unpurchased add-ons

When a user reaches a paid add-on without owning it — either by tapping its entry-point icon (if
somehow still enabled, e.g. mid-purchase-flow) or, more commonly, discovering it via an
in-app "Get more apps" surface — show a simple locked-state screen: app name/icon, a short
description (reuse existing marketing copy conventions from the desktop `README.md`'s per-app
feature lists where applicable), price, and a "Buy" button driving the flow in §7b. This screen
is new UI, scoped fully in the relevant per-app Android document (§11) once that phase starts —
not designed in detail here.

An **"Add-ons" or "Get more apps" entry** somewhere in the free tier's navigation (candidate:
`MobileMoreSheet`, per BACKLOG.md §4c) is the discovery surface for a user who never sees
Notes/Portfolio/Fitness's entry-point icons because they were never enabled. Exact placement is
a per-app-phase design decision, flagged here so it isn't forgotten when writing that phase.

### 7e. `isAppEnabled()` implementation

**See ADR-5 for the actual implementation** (`isAppEnabled()` + `useIsAppEnabled()`, both keyed
off `ANDROID_PAID_APPS`, not `APP_TIERS`) — not repeated here to avoid two copies of the same
code drifting apart, which is exactly what happened in this document's first draft (an earlier,
buggy version lived here, keyed off `APP_TIERS` and using the now-replaced fixed-boolean-field
entitlement shape; an audit caught both problems — see ADR-4 and ADR-5's "Corrected from this
document's first draft" notes).

Two of the three existing call sites need a small change, not zero: `NavSidebar` and `App.tsx`'s
section-routing JSX must switch to `useIsAppEnabled(view)` for correct re-rendering on
purchase/hydration (ADR-5); the `6`/`7` nav hotkey handler can keep calling the plain
`isAppEnabled(view)` unchanged, since it already runs outside render. Beyond that one hook swap,
this is the entire integration surface with the existing desktop code — everything else in this
monetization section is additive, new files.

## 8. Cross-app integration on Android — why it needs no special work

Because ADR-1/ADR-2 keep this one app/one process regardless of which entry point launched it,
every cross-app mechanism the desktop suite already relies on keeps working with zero Android-
specific code:

- **Purposes** tag across apps identically — same `taskStore`, same Purpose entities, whichever
  entry point opened the app.
- **The in-process event bus** (e.g. Portfolio emitting `'create-task'`) fires exactly as on
  desktop — it's an in-memory emitter in a shared package, and there is exactly one memory space
  regardless of entry point.
- **Supabase auth session** is a single session for the whole app, same as desktop — signing in
  from any entry point authenticates the whole suite.
- **The Endeavour filter, Manage view, Sidebar** — all per-section or global `uiStore` state,
  unaffected by which icon launched the process.

The only genuinely new behaviour Android introduces is *which section is active on launch*
(§4.4) — everything downstream of `setActiveView()` is identical to how switching sections via
the desktop nav already works. Do not build any Android-specific cross-app plumbing; if a future
agent finds themselves writing one, that's a signal something upstream was misunderstood.

## 10a. Testing & verification workflow

Applies to every phase in this document set — referenced from each per-app document rather than
repeated in each one.

**Primary development loop (fast iteration):** point the native shell at the running Vite dev
server instead of rebuilding on every change. Temporarily add to `capacitor.config.ts` (never
commit this):
```typescript
server: { url: 'http://YOUR_LOCAL_IP:5173', cleartext: true }
```
then `npx cap sync android` once and run from Android Studio — subsequent code changes hot-reload
on the emulator/device exactly like the browser dev server does, no rebuild-and-resync cycle
needed per change. Remove this block before any real build.

**Verifying a finished phase (production-like):** `npm run build` → `npx cap sync android` →
`npx cap open android` → run on an AVD from Android Studio. This is exactly the workflow already
scripted in `package.json` (`build:android`/`open:android`/`sync:android`, per BACKLOG.md §1) —
loading the generated `android/` project in Android Studio and running it on a virtual device is
the correct, standard way to test a Capacitor app; nothing more exotic is needed.

**Emulator (AVD) configuration:** create an AVD on a recent API level (34+, matching the target
SDK) using a **"Play Store"-flavoured system image**, not a bare "Google APIs" one — only the
Play Store-flavoured images include the actual Play Store app and Play Billing support, which
matters once Track B testing starts. Touch gestures (taps, swipes, drags) all work fine via
mouse simulation in the emulator.

**Where the emulator is not representative — test on a real device before considering a phase
done:**
- **Haptics** — emulators simulate vibration weakly or not at all; a phase that wires up
  `hapticLight()`/`hapticSuccess()` needs a physical device to confirm it actually feels right.
- **Play Billing purchase flows** — can partially work on a Play Store-flavoured AVD signed into
  a test account, but the real flow (and Play Console's license-tester setup) is only fully
  representative on a physical device tied to a real Google account added as a tester.
- **Camera capture** (if/when built per ADR-8) — emulators use a simulated camera; fine for
  confirming the capture flow calls the right store action, not for judging real photo quality.
- **Notifications** — local notification scheduling/display works on emulators, but confirm on
  a real device too before shipping, since OEM battery-optimisation behaviour (which can delay
  or kill scheduled notifications) varies in ways an emulator won't reproduce.

## 11. Phased roadmap beyond this document

This document is Phase 0. Each subsequent phase is its own file in `docs/android/`, written and
reviewed before the next begins — per the explicit instruction to build stepwise rather than
going deep on unreviewed assumptions.

Numbered to match each free app's position in CLAUDE.md's own nav-hotkey order (Tasks=1,
Calendar=2, Records=3, Lists=4) — notifications and the paid add-ons follow, since they aren't
"the Nth app" in that same sense.

| Phase | Document | Scope |
|---|---|---|
| 0 | `00-architecture.md` (this file) | Foundation: process model, entry points, layout system, entitlements/billing/ads architecture |
| 1 | `01-tasks-app.md` | Full Android UX spec for Tasks — every screen, gesture, and behavioural difference from desktop |
| 2 | `02-calendar-app.md` | Full Android UX spec for Calendar, including Schedule's "accessible but not optimised" scope |
| 3 | `03-records-app.md` | Full Android UX spec for Records (trackers + routines) — master-detail collapse pattern, quick-log for single-field trackers |
| 4 | `04-lists-app.md` | Full Android UX spec for Lists (watchlists + reference lists) |
| 5 | `05-notifications.md` | Full notification spec (carries BACKLOG.md §6 forward with Schedule/Fitness deltas) — not a hard blocker for phases 1–4, see the note below |
| 6+ | `06-notes-app.md`, `07-portfolio-app.md`, `08-fitness-app.md` | Paid add-ons — written once the entitlement/billing foundation (this doc, §7) is built and proven with at least one real add-on purchase flow |
| — | `09-build-release.md` | Signing, Play Console listing setup, phased rollout (internal testing → closed → production), written once Phases 1–4 are functionally complete and there's something real to release |

**The numbering is a filing convention, not a build-order dependency.** Every free-app phase
(1–4) needs only Track A (§10) from this document — none of them needs phase 5 (notifications)
done first, or done at all, to be built and fully tested. Notifications are an enhancement layer
on top of already-working entities (a task/event/routine works completely on its own; a
notification just reminds you about it) — build phase 5 whenever convenient relative to 1–4, not
because its number comes after them. The only real dependency chain in this whole roadmap is
Track A → any free-app phase, and Track A + phase 5's entitlement pattern → Track B → any paid
add-on phase (6+).

Each per-app document should assume this file's architecture as given and cross-reference it
(`see docs/android/00-architecture.md §4` etc.) rather than re-explaining entry points,
entitlements, or the mobile layout system from scratch.

## 12. Explicitly out of scope

- iOS, in any form (ADR-7).
- Subscriptions — every purchase in this plan is one-time/non-consumable.
- Separate APKs per app — explicitly rejected in favour of ADR-2/ADR-3.
- Server-side receipt validation as a launch blocker — flagged in §7b as a pre-wide-release
  hardening step, not required for internal testing.
- Interstitial or rewarded ads — banner only, for now (§7c).
- Any redesign of desktop/web behaviour — `isAppEnabled()`'s new logic is Android-conditional
  and changes nothing for the platforms that already ship.

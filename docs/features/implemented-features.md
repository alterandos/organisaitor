- [x] **Calendar entry kinds, clarified — deadline (`kind:'task'`) vs scheduled (`kind:'event'`) are intentionally different, now made visually legible**: an audit found that `Task.deadline` renders as a first-class `kind:'task'` calendar item (opens `TaskPane`, gets completion styling) while `Task.scheduledAt` renders as a `kind:'event'` via its auto-created shadow `CalendarEvent` (opens `CalendarEventPane`, no completion styling) — raising the question of whether this was a bug. **Resolved as intentional, not a bug**: a scheduled task genuinely blocks calendar time the way a real event does (that's the whole point of giving it a time), so it correctly stays a `CalendarEvent`, not a same-shaped `task` item. What *was* missing was any visible sign that a given event is task-derived. Fixed two ways: (1) `CalendarView.tsx`'s `itemsByDate` builder now sets an event's `typeIcon` to `🕐` whenever any task's `calendarEventId` points at it (a `Set<CalendarEventId>` built once per render from `Object.values(tasks)`, checked after the pre-existing birthday-🎉 check) — reuses `typeIcon`, the same generic field already driving the birthday icon and the Schedule 🗓, so every view (month/week/day/day-pane) picks it up for free with no per-view code; (2) `CalendarEventPane.tsx` looks up `Object.values(tasksRecord).find(t => t.calendarEventId === event.id)` and, when found, renders a `🕐 Linked task: <title>` chip (`.linkedTaskChip`) above the title input — clicking it calls `closePane()` then `openTaskPane(task.id)`, a clean swap (not a stacked pane) straight to the real task. The emoji scheme (❗ deadline, 🕐 scheduled, ⏳ waiting) deliberately reuses `TaskItem.tsx`'s existing pill icons rather than inventing new ones, so the task list and the calendar read consistently. `kind:'waiting'` tasks have no dedicated date field yet — they use the same `deadline`/`scheduledAt` as any other task kind, so a distinct "waiting since" calendar indicator is a future schema addition, not something wired up now.

- [x] **Desktop week view — real hourly time grid** (`CalendarView.tsx`): replaced the old agenda-list week view (items just stacked as pills per day column, no time-of-day positioning at all) with an actual time grid, matching how Google/Outlook/Apple Calendar look — items are vertically positioned and sized by their actual start/end time, with side-by-side layout for overlapping items.
  - **Hour compression, the actual "elegant" ask**: hours with nothing scheduled *anywhere in the visible week* collapse to a thin row (`HOUR_HEIGHT_EMPTY = 18px`); hours with content anywhere expand to full height (`HOUR_HEIGHT_ACTIVE = 60px`). This is a **shared row template across all 7 day columns** — computed from the union of activity across the whole week, not per-day — so the columns stay vertically aligned (a day with nothing at 9am still gets a full-height 9am row if some *other* day in the same week has something then). `buildHourLayout(activeHours)` returns per-hour pixel offsets/heights; `minutesToY()` interpolates any minute-of-day into a pixel position against that layout, including fractional positions within a compressed hour for an event spanning through otherwise-empty time.
  - **Overlap layout**: `layoutDayTimeGrid()` is a small greedy interval-graph-colouring pass — overlapping items within a day split into side-by-side columns (each `100/totalCols`% wide) instead of fully overlapping each other, the same visual language every mainstream calendar app uses for double-booked time.
  - **Duration handling**: `CalDisplayItem` still only carries a single `time` field (shared across tasks/events/reminders), so the grid looks up the full `CalendarEvent` from the raw `events` record by id when it needs `endTime`. An event with no `endTime` defaults to a 60-minute visual block; a task/reminder (point-in-time, no real duration) defaults to 30 minutes — both are display-only assumptions, no data model change.
  - **Untimed items row**: tasks/reminders with no time-of-day get their own small row (`weekUntimedRow`) above the hourly grid, same idea as an "all-day" strip in other calendar apps — kept structurally separate from the pre-existing multi-day-event `weekSpanRow` above it (different data source — `getWeekSpanSlots` vs. plain per-day untimed filtering — deliberately not unified, to avoid touching the already-working span-row logic).
  - **"Now" line**: a red line + dot across today's column at the current time, recomputed via a `setInterval` every 60s while week view is active (`nowTick` state) so it drifts correctly without needing every unrelated store update to trigger a re-render. Uses the account's effective timezone (`resolveTimezone`/`utcToZonedTime`), consistent with the rest of the timezone feature.
  - **Auto-scroll**: on entering week view (or changing the selected week), the scroll container jumps to just above the first active hour, so a day that only has evening events doesn't open scrolled to a wall of empty morning.
  - **Hour labels respect `clockFormat`**: reuses `formatTime()`, so 24h/12h/system all render correctly (verified live in both modes).
  - Not built (deliberately out of scope for this pass): click-and-drag to create an event at a specific time (clicking a day column still just opens `AddCalendarItemModal` for that date, unprefilled with a time, matching the pre-existing month-view click-to-add behaviour), and drag-to-resize/reschedule an existing block.

### Location integration — options considered, not yet built

The user asked, as a planning question (not yet scoped for implementation): the app's `CalendarEvent.location` is (and after the ICS import work above, will keep being) a plain free-text field — no autocomplete, no geocoding, no map. What would it take to get something like Google Calendar's location handling (which itself is backed by Google Places)?

Three tiers were identified, cheapest first:

1. **"Open in Maps" link only, no API/key needed** — wrap whatever free-text `location` string already exists into a Google Maps search URL (`https://www.google.com/maps/search/?api=1&query=<url-encoded text>`). Zero setup, no billing, no new dependency — extends the exact pattern `CalendarEventPane.tsx`'s existing `isLocationUrl()` special-case already uses (a location that "looks like a URL" gets rendered as a clickable link today; this would add "or just always offer a maps-search link regardless of what the text looks like"). No autocomplete, no map preview, no normalized/validated address — but real and shippable in a small change to `CalendarEventPane`/`AddCalendarItemModal`, no new integration credentials.
2. **Geocode + static map preview on blur** — one-shot lookup (Google's Geocoding API, or an alternative like the free/keyless OpenStreetMap Nominatim for a lower-fidelity option) turns the typed text into a normalized address + lat/lng once the field loses focus; a small embedded map preview via the Maps **Embed** API (a plain `<iframe src="https://www.google.com/maps/embed/v1/place?...">`, no JS SDK) shown in `CalendarEventPane`. Needs a Google Cloud project + a Maps Platform API key (Google's Maps Platform has a recurring free monthly credit, but does require a credit card on file — same category of setup as the existing Strava integration, though Places/Maps keys are safe to expose client-side when restricted by HTTP referrer in the Cloud Console, unlike Strava's server-only client secret).
3. **Full Places Autocomplete-while-typing** (closest to actual Google Calendar behaviour) — Google's Places Autocomplete Element suggests real places as the user types, returning a `place_id` resolved via Place Details into a normalized address + coordinates. This is the option with real data-model impact: `CalendarEvent.location` would need to become a structured value (`{ formattedAddress, placeId, lat, lng }` alongside — or instead of — the current plain string), which is a schema/migration change in the same category as the archiving/`collectionId` additions this app has done before, plus a Supabase migration and mapper update. Google's Autocomplete pricing bills per session (bundling the keystroke suggestions and the follow-up details fetch together) rather than per keystroke, which keeps cost bounded but still real.

**Tier 1 implemented** (recommended as the pragmatic "ship the basic layer now" starting point — genuinely a ~15-minute, zero-dependency, zero-credential change, and nothing about it needs to be un-done to later add Tier 2/3, since those both still start from the same plain-text address the user types today): `CalendarEventPane.tsx`'s Location field now always shows a link icon next to the text input whenever `location` is non-empty — 🗺 wrapping the typed address into a Google Maps search URL (`https://www.google.com/maps/search/?api=1&query=<encoded>`) via a new `locationMapsUrl()` helper, or ↗ (unchanged) when the stored value already looks like a URL (`isLocationUrl()`, pre-existing). No API key, no new dependency, no schema change — purely a URL-construction addition, so Tier 2/3 later (an actual Places integration) simply replaces this link with something richer rather than needing to remove anything. Deliberately not added to `AddCalendarItemModal` (a creation pane) — matches the pre-existing rule that creation panes render links-in-progress as plain text inputs, not live clickable links, until the item is saved.

  - **Remote silently overwrote local edits with no recency check.** The old merge was `{...local, ...remote}` per entity — for any ID existing in both, remote *always* won, unconditionally. An item edited locally while offline (archived, re-titled, whatever) but already present in Supabase from a prior sync would get reverted back to its stale remote copy on the next login/refresh.
  - **Fix**: switched to soft-delete tombstones. New migration `supabase/migrations/013_soft_delete.sql` adds `deleted_at timestamptz` to all 7 synced tables (`tasks`, `collections`, `tags`, `purposes`, `calendar_events`, `calendar_reminders`, `tracker_entries`) — applied to the live project (see "Live migration status"). The delete path (now `pushIds()` in `syncService.ts`; it was `syncDiff()`) does `.update({ deleted_at: now })` instead of `.delete()`. `hydrateStores()` was rewritten around a new `mergeRecords()` helper (per entity type, generic over the row shape): a remote row with `deleted_at` set removes the local entry outright; otherwise, local and remote are compared by `updatedAt` and the newer one wins (a local-only entry with no remote row at all — the "created offline, not yet uploaded" case — is left untouched either way, since it matches neither branch). `Tag` has no `updatedAt` field in the domain model, so it deliberately keeps the old "remote wins" behavior for edits (still tombstone-aware for deletes) rather than adding a field this fix didn't otherwise need. `runInitSync`'s `isEmpty` check (which decides whether to push local→cloud on a fresh account vs. pull cloud→local) was also updated to only count *live* rows, so an account containing nothing but tombstones is still correctly treated as empty.
  - **Also fixed, same incident**: `initSync` and `forceUpload` could previously run concurrently and interleave (e.g. the page-load-triggered `initSync` still in flight while a manual restore-triggered `forceUpload` runs), each reading/writing store state out of order — plausibly why a prior force-upload attempt appeared to succeed with no error but didn't actually push the expected rows. Both now funnel through a shared `enqueue()` promise-chain mutex in `syncService.ts`, so one always fully completes before the other starts.
  - **New: a direct "Force upload this device's data to cloud" button** in `AccountPane.tsx` (signed-in state, above Export/Restore) — calls `forceUpload()` on live in-memory state directly, no localStorage round-trip and no page reload required (the old recovery path was Export → Restore-from-that-same-file → reload, which is exactly the sequence that could race against a concurrent `initSync`). Reports back exact per-table counts (`UploadCounts`, now returned by `forceUpload()` instead of `void`) so the result is verifiable without opening Supabase directly.
  - **Known gap, not addressed here**: no purge/cleanup of old tombstones — `deleted_at` rows are kept indefinitely. Fine at current data scale; worth revisiting if these tables grow large enough to matter.
  - **Sign-out no longer emits a cloud-wide soft-delete (2026-09-19)**: `authStore.signOut()` wipes the in-memory synced stores as a local cache clear, but the sync subscription was still live, so the change tracker (then `syncDiff`, now `trackChanges`) read the wipe as "the user deleted everything" and fired `PATCH … deleted_at` for every row of tasks/collections/tags/purposes/events/reminders/tracker_entries. It was rejected (401) only because `supabase.auth.signOut()` had already revoked the token — a data-loss bug protected purely by ordering luck. `signOut` now calls `stopSync()` first. **Any future code that bulk-clears a synced store must stop sync first.** *(The adjacent gap this entry used to record — notes/lists/schedules/portfolio surviving sign-out — was closed 2026-09-20; see "Sign-out clears this device's synced data".)*
  - **Vault status and tab refocus**: `checkVaultStatus` early-returns when the vault is already unlocked in memory — Supabase re-fires `SIGNED_IN` on tab refocus/token refresh, which would otherwise re-lock an unlocked-but-not-"trusted" vault every time.
  - **Per-table failure isolation (2026-09-19)**: `runInitSync` used to fetch every table in one `Promise.all` and throw on the first error, so a single unreadable table (e.g. the just-added Notes/Portfolio tables 403ing for want of a grant) blocked *every* table from hydrating — Tasks/Trackers vanished even though nothing was wrong with them. Now a failed table comes back as `null` (a no-op for `mergeRecords`), is logged and named in the sync status error ("Could not sync: notes, … (other data synced normally)"), and suppresses the "remote looks empty → push local up" branch (an unreadable table could be hiding real remote data). `SYNC_TABLES` in `syncService.ts` must stay in the same order as the fetch list. **When adding a new synced table, add it to both.** The vault mirrors this: `VaultStatus` has an `'unavailable'` state for an unreadable `user_vault` (distinct from `'locked'`, and never treated as `'not-set-up'`, which would invite creating a second vault over the first).

Wraps correctly past midnight (`dayOffset` in the return value bumps a paired end-*date* field when the caller has one). Implemented as one pure, reusable function, `computeLinkedEndTime(startTime, currentEndTime)` in `src/utils/date.ts` (alongside a new `addDaysToIso()` helper), wired into every start/end time pair in the app: `AddCalendarItemModal`, `CalendarEventPane` (both also bump `endDate` on rollover), and `AddScheduleModal`'s block editor (both the "+ Add block" form and existing block rows — no rollover concept there, since a weekly recurring block has no date to bump).

  - **Non-AI smart pre-fill** (`src/utils/textToTask.ts`, `inferTaskFromSelection(text, now)`): regex-based, no external dependency, locale-aware via `Intl` where genuine ambiguity requires a convention choice. Infers four things:
    - **Date**, in priority order: relative terms (`today`/`tomorrow`/`this weekend`/`next weekend`/`next Friday`/`in 3 days`/`in 2 weeks`/bare weekday names), ISO `YYYY-MM-DD`, `Month Day[, Year]` / `Day Month[, Year]` (abbreviated or full month names, ordinal suffixes tolerated), and numeric dates with `/`, `-`, or `.` separators. Numeric resolution: one part > 12 is always unambiguous regardless of separator; when both parts are ≤ 12, `/` accepts it without a year (the older, looser rule — "/" is a strong date signal on its own) while `-`/`.` **require** a year (a bare `10-15` or `3.14` is far more likely a page range or a decimal than a date, so those are only read as dates once a year makes the intent clear, e.g. `11/09/2029` or `11-09-2029`). A genuinely ambiguous pair *with* a year present is resolved via `Intl.DateTimeFormat().formatToParts()` to detect day-before-month vs. month-before-day for the runtime's locale (`isDayFirstLocale()`), rather than hardcoding either convention. Internally, higher-priority matches are "claimed" by blanking their span (space-padded, so indices stay valid) before lower-priority patterns scan the remainder — prevents e.g. an ISO date's own digits from also matching as a nested numeric-dash candidate. A year omitted from the text resolves to the current year, rolled forward one year if that date has already passed (`resolveYear()`) — "by 5 March" typed in September infers next March, not the one already gone; an explicit year is always respected as-is even if it's in the past. Candidate dates found within ~30 characters after a trigger word (`by`/`due`/`deadline`/`before`/`until`/`on`) are preferred over earlier matches elsewhere in the text.
    - **Time**, once a date was found: `6pm`/`18:00`-style patterns, plus `noon` → 12:00 and `midnight` → 00:00.
    - **Priority** (`inferPriorityFromText`): keyword-based, checked high-to-low so weak/generic words don't misfire — `urgent`/`asap`/`critical`/`high priority`/`!!` → high; `low priority`/`no rush`/`not urgent`/`whenever` → low; `medium priority` (only with the explicit word "priority" — bare "medium" is too generic to trust alone) → medium; otherwise `null` (caller defaults to `'none'`, never silently overridden).

    - **Two more real bugs, caught via live round-trips, both belonging to the "a popover embedded inside a scrollable modal" problem class — worth knowing about before building the next such popover in this codebase**:
      1. **Escape closed the whole `AddTaskModal`, not just this picker's dropdown.** Same root cause already documented elsewhere in this file (ManageSchedulesPane/AddScheduleModal): two independent bubble-phase `document` `keydown` listeners (the modal's own, and this picker's) both react to Escape, and `stopPropagation()` from the *second*-registered one can't retroactively stop the *first* one, which already ran. The general fix used before (an inner layer checking "is my outer layer's modal open" and skipping) doesn't fit here because `CrossAppRefPicker` is a generic, embeddable component with no idea what it's embedded inside. The fix that *does* generalize: register the picker's Escape listener on `document` in the **capture phase** (`addEventListener('keydown', handler, true)`) and call **`stopImmediatePropagation()`**, not `stopPropagation()`. A capture-phase listener on `document` always fires before *any* bubble-phase listener anywhere in the tree, regardless of which mounted first, and `stopImmediatePropagation()` (unlike `stopPropagation()`) actually prevents a later sibling listener on the identical target from running at all. This is the more robust version of the earlier fix, and arguably how that one should be described too: check-the-outer-layer works when you own the outer layer; capture-phase-plus-stopImmediatePropagation works even when you don't.

Even though an absolutely-positioned element doesn't affect *normal-flow* layout, it still contributes to its scrollable ancestor's `scrollHeight` when it extends past the ancestor's flow-determined content box. Clicking the submit button first dispatches `mousedown`, which the picker's own outside-click handler sees and reacts to by closing the dropdown — shrinking the modal's `scrollHeight` — which caused the browser to clamp/adjust the modal's scroll offset *between* that `mousedown` and the following `mouseup`. The submit button physically moved to a different position on screen mid-click, so the `mouseup`/`click` landed on whatever was now underneath the cursor (confirmed via event-target tracing: it landed on the picker's own chip row) instead of the button — `AddTaskModal.handleSubmit` was simply never called. Fixed by portaling the dropdown to `document.body` with `position: fixed`, computed from the trigger button's own `getBoundingClientRect()` (clamped to stay within the viewport, flipping above the trigger if there isn't room below) — removing it from the scrollable ancestor's layout entirely, the same fix shape already used elsewhere in this app (`NoteEditor`'s table hover controls, `LinkHoverPreview`) for exactly this class of problem. **General lesson for this codebase**: any dropdown/popover that can be embedded inside a form long enough to scroll should be portaled from the start, not added in-place — the failure mode is silent (no error, no visual glitch, just an unresponsive button) and only reproduces in that one specific "acted on the popover, then immediately clicked something below it" sequence, easy to miss without a live round-trip test.

Worth knowing before relying on this for something sensitive.
  - **Storage model — one envelope, sensitive fields blanked, at every layer.** An encrypted note's sensitive fields are serialised into one `NoteSecrets` object, AES-GCM-encrypted with the vault key into `Note.encryptedPayload`, and **emptied on the stored object** (`title: ''`, `content: ''`, `abstract: null`, `tabs: []`, `tagData: {}`). That blanked form is what lives in zustand state, in `notes-storage` localStorage, and in Supabase (`notes.encrypted_payload`, migration `024`) — so a leaked localStorage dump is as unreadable as the cloud row, and **`syncService.ts`/`mappers.ts` stayed dumb pass-throughs with zero crypto awareness** (which is why none of the sync merge/tombstone logic changed). `StructuredTagEntry` gets the same `isEncrypted` + `encryptedPayload` pair (`term: ''`, `fields: {}` while stored). `noteStore` bumped to **v12** (backfills both fields).
  - **Plaintext lives only in a memory cache** (`src/services/noteSecrets.ts`): a `Map` per entity, never persisted, filled while the vault is unlocked and wiped on lock. A cache entry is trusted only while it matches the note's current `encryptedPayload` (a sync pull that replaces the payload makes it stale until re-decrypted) or is `dirty` (an edit applied to the plaintext whose re-encryption hasn't landed yet).
  - **THE RULE: read an encrypted note only through `noteView(note)`** (or `useNoteView(id)` / `useNoteViews()` / `useEntryViews()` in React — `src/store/noteViews.ts`), never `note.title`/`.content`/`.abstract`/`.tabs`/`.tagData` straight off the store: those are blank for an encrypted note. `noteView` returns the plaintext when the cache has it, or a locked placeholder (`title: 'Encrypted note'`, everything else blank) when it doesn't; `isNoteLocked(note)` says which. Converted to read views: `NoteEditor`, `NoteList`, `TagView`, `quickAccess`, `CrossAppRefPicker`, `EditNoteMetaModal`, `NoteEditorPane`, `crossAppLinkCleanup`. **Any new code that displays or searches a note's text must do the same** — forgetting it shows a blank/"Encrypted note" instead of the text, and (worse) writing such a blank back would destroy data, which is why writes are centralised (next bullet).
  - **Writes go through the store actions, which route encrypted notes themselves.** `updateNote`, `addNoteTab`/`removeNoteTab`/`renameNoteTab`/`updateNoteTabContent`/`renameMainTab`, `updateStructuredTagEntry` all funnel through `editNote`/`editEntry` (module-level in `noteStore.ts`): for a plain note that's the old behaviour; for an encrypted one the edit is applied to the cached plaintext *immediately* (the UI never waits on crypto), the stored object is re-blanked, and a background re-encryption is queued (`queueEncrypt`, one in-flight per note, **always encrypting the latest secrets** — otherwise an older payload could land after a newer one and silently revert the note; verified with a 25-edit burst). An edit to a **locked** encrypted note is refused with a console warning rather than risk corrupting it. `addStructuredTagEntry` on an encrypted, unlocked note creates the entry born-encrypted. `NoteEditor` no longer contains any crypto — it saves plaintext like it always did.
  - **New actions**: `encryptNote(id)` (rejects if the vault is locked — never falls back to plaintext), `decryptNote(id)` (rejects if the note's plaintext isn't available), both also converting the note's entries; `upgradeLegacyEncryptedNote(id)`.
  - **Legacy upgrade**: notes encrypted by the first version (only `content` encrypted, title etc. plaintext, no `encryptedPayload`) are folded into the new all-fields payload automatically the next time the vault is unlocked (`noteSecretsSync.ts` → `upgradeLegacyEncryptedNote`). Failures are remembered so an unreadable legacy note isn't retried on every store change.
  - **`noteSecretsSync.ts`** (started from `App.tsx`): re-runs on every vault-status change and every notes/entries change — decrypts whatever encrypted note/entry has a missing or stale cache entry (so unlock, trusted-device auto-unlock and notes pulled in by sync all just work), and clears the whole cache whenever the vault isn't unlocked.
  - **Locking is now sticky and safe.** `lockVault()` is async: it runs **`flush` hooks** first (`NoteEditor` pushes its pending autosave/title/abstract debounces into the store, which queues their encryption), then **`settle` hooks** (`flushEncryptions()` waits for every queued re-encryption to land), *then* drops the key — so locking can never discard an in-flight edit. Two phases because they depend on each other and registration order can't guarantee it (the settle hook registers at app start, long before an editor mounts). It then also **calls `untrustThisDevice()`** and sets a `manuallyLocked` flag. **Root cause of "locking doesn't stay locked"**: Lock now used to clear only the in-memory key and leave the trusted-device copy in IndexedDB, and Supabase re-fires `SIGNED_IN` on every tab refocus, so `checkVaultStatus` found the cached key and quietly unlocked again. The cost of sticky locking: after a deliberate lock you type the passphrase once to unlock (tick "Trust this device" to re-cache it). *Not root-caused*: the separate report that the Account pane didn't visibly update after clicking Lock — not reproducible from the code; possibly the same re-unlock racing the click. Re-test.

  - **Is it strong enough for passwords / banking details? Honest assessment (recorded because it was asked directly):** the *cipher* is — AES-256-GCM with a random per-vault key, a fresh random IV per envelope, authenticated (tampering is detected), and the server never sees a key. The *practical* strength is bounded by weaker links: (1) **the passphrase** — the vault key is wrapped with PBKDF2-SHA256 at 250,000 iterations; if a cloud dump leaked, an attacker can guess passphrases offline, and the setup form only requires 8 characters, which is weak against that. A long passphrase (5+ random words) makes it strong; a short one doesn't. (2) **plaintext exists while unlocked** — in memory and the DOM, and (with "Trust this device") the unwrapped key sits in plain IndexedDB on that device, so anyone with access to an unlocked/signed-in machine or its browser profile can read it; encryption protects the *cloud copy*, not a compromised device. (3) **metadata is not hidden** — the server sees that a list exists, its kind/colour/icon, item counts, tab structure, timestamps. (4) **no recovery beyond the passphrase or the recovery code** — lose both and the data is unrecoverable, by design. (5) **the unencrypted local copies of anything created *from* encrypted content** (e.g. a Task created from an encrypted note) are separate plaintext. Net: fine for sensitive lists to keep out of the Supabase operator's view, *provided the passphrase is strong*; for high-stakes secrets (banking, master passwords) a dedicated password manager is still the better tool. Possible hardening, not built: a passphrase-strength meter / longer minimum, raising PBKDF2 iterations or moving to Argon2 (needs a WASM dependency), OS-keychain storage for the trusted-device key, auto-relock after inactivity.

  - **Files:** `supabase/migrations/032_oauth_state.sql`; `src/services/oauthState.ts` (`mintOAuthState(provider)` → `supabase.rpc('mint_oauth_state')`); `src/services/strava.ts` and `src/services/googleCalendar.ts` (connect-URL builders now `await mintOAuthState(...)` and throw if it fails); `FitnessSection.tsx` / `CalendarSidePane.tsx` (`handleConnect` catch the throw and show it — as a message / `alertDialog`); `api/strava-oauth-callback.ts`, `api/google-calendar-oauth-callback.ts` (rewritten); `api/_lib/supabaseEdge.ts` (new `getAnonClient()`; `getUserClient()` is still used by every Bearer-authenticated endpoint).
  - **Flow:** signed-in client calls `mint_oauth_state` (security definer, uses `auth.uid()`; ≥244-bit nonce from two `gen_random_uuid()`s; 10-minute expiry; one live nonce per user+provider, so starting again invalidates the previous one and the table stays small) → nonce goes in `state` → provider redirects to the callback → the callback exchanges the `code`, then calls `save_strava_connection` / `save_calendar_connection` **with the anon key**. Those functions `delete … where nonce = … and provider = … and expires_at > now() returning user_id` — validation and consumption are one statement, so a second presentation can never succeed — and upsert the connection row for that user. Unknown / reused / expired / wrong-provider all come back as `invalid_state` (deliberately not distinguished) and the callback redirects to `/?strava=error&reason=invalid_state` (or `googleCalendar=`). The Google function also keeps the stored refresh token when the response carries none (logic moved from the callback into SQL, since the callback can no longer read the row).
  - **Decisions:** chose brief option A (nonce table + security-definer functions) because it preserves the invariant *no Supabase service-role key anywhere*. Rejected B (signed state + service-role key in two callbacks: bypasses RLS, new Vercel secret) and C (finish the OAuth in the SPA: the Tauri/Android webviews have no session at the Vercel-origin redirect destination). `oauth_states` has RLS on, no policies and no grants; each function is `revoke … from public, anon, authenticated` then granted to exactly the role that needs it (Postgres and Supabase both grant `execute` broadly by default), and uses `set search_path = ''` with schema-qualified names.
  - **Login-CSRF (accepted residual risk, recorded on purpose):** an attacker with their own account can mint a nonce and trick a *victim* into approving the provider's consent screen, which would attach the victim's calendar/Strava to the attacker's account. The old design resisted this only because the state was the victim's own secret. Binding the nonce to the starting browser needs a value that lives in that browser and reaches the callback — a cookie on the Vercel origin — but the Tauri and Android webviews start the flow from a different origin (`tauri.localhost` / `capacitor://`), and a binding the attacker can opt out of (by starting from "another platform") protects nothing, so it was not added half-way. Mitigations that do exist: the nonce is single-use and 10 minutes long, the attacker must first get the victim to open a provider consent URL and approve it, and the scopes are read-only (`calendar.readonly`, `activity:read`). A proper fix is to run the flow in the system browser with a deep-link return and a PKCE-style verifier held by the app (tracked in BACKLOG.md "OAuth flow hardening").

- [x] **Sync that survives offline: pending-changes queue, reconcile after load, retries** (2026-09-22).
  - **Why:** reading the sync code (asked by the user: "do I need to force upload to close the app safely?") showed pushes were fire-and-forget. A change made offline, or whose request failed, was never retried; an item edited or created offline was kept locally by the load's merge but never uploaded (only "remote is completely empty" uploaded everything); a deletion made offline was undone by the next load (the cloud row was still alive, so the merge restored it); and a request in flight when the window closed was lost.
  - **What (`syncService.ts`):** (1) a **pending-changes queue** — `watch()`/`trackChanges()` record each changed/deleted row id (`markDirty`) in localStorage `todo-sync-pending` before sending, and `pushIds()` sends the row's current state or a soft-delete and forgets the entry only on success (an entry re-marked while its request was in flight is kept, via a per-entry sequence number); (2) **retries** — `flushPending()` on `online`, every 60 s while anything waits, and after each load; status shows `error … will retry (N changes waiting)` and returns to `idle` when the queue empties; (3) **reconcile after the merge** — `queueLocalOnlyAndNewer()` queues local-only rows and rows whose local `updatedAt` is newer than the cloud's `updated_at`, for tables that loaded; (4) **no resurrection** — `mergeRecords()` skips a live remote row whose id is pending-deleted here; (5) `TABLE_DEFS` registry replaces the seven hand-written subscriptions and `syncDiff` (behaviour unchanged for online use: still an immediate push per change, batched per table); (6) `forceUpload` also flushes pending soft-deletes; (7) `authStore.signOut` clears the queue after the wipe, and a queue belonging to another account is discarded on load (from disk too).
  - **Also:** `NoteEditor` flushes its pending autosave on `pagehide` / tab-hidden — closing the window used to lose the last ~1.5 s of typing, which never reached the store, the local database or the cloud.
  - **Decisions:** the queue holds ids, not payloads, so several offline edits collapse into one push of the latest state; last-write-wins on `updatedAt` stays (no field-level merge); a remote tombstone still beats a local edit (unchanged); the queue is not backed up (per-device bookkeeping — a restored copy would replay stale changes). Rejected: a periodic full re-pull (heavy — every load already downloads every row) and realtime subscriptions (out of scope; another device's changes still arrive only on its next load).
  - **Verified** in headless Edge against a simulated Supabase (requests intercepted with an in-memory PostgREST fake that can be switched offline; 22/22): a task created offline is recorded on disk, absent from the cloud, uploaded on the next launch even though the cloud wasn't empty; a task deleted offline stays deleted after relaunch and the cloud row gets its deletion marker while the other task is untouched; a task edited offline keeps its edit through the merge and reaches the cloud; a change made offline is pushed when the browser fires `online` (no restart) and status returns to `idle`; relaunching a fully in-sync app performs no writes; an online change is pushed immediately and leaves nothing pending; another account's queue is reset (on disk) and `clearPendingSync()` removes it. Regressions: link/tab suite 24/24, list-popover 10/10, IndexedDB 18/18. `tsc -b` clean, `npm run build` passes, `NoteEditor.tsx` lint unchanged (8, pre-existing). **Not verified against the real Supabase project** (no test credentials/session in the harness — the fake models `select`, `upsert` and soft-delete `update` only); per-table RLS/permission failures; two devices editing at once; the first launch after upgrading with a large pre-existing offline backlog.
  - **Not built / known gaps:** local *deletions* made in the moment between opening the app and the load finishing (subscriptions are torn down and rebuilt around the fetch) are not tracked, so such a deletion can be undone by that load — edits and creations in that window are covered by the reconcile; no realtime or periodic pull; no conflict UI; tables without `updatedAt` can't detect an offline edit; a note with large inline images still sends the whole row on every autosave.

  - **Testing note — a real production concurrency bug found via the test suite, not a test-isolation artifact**: `addScore()` only reset the running score to 0 *after* `buildBackupSnapshot()`/`saveBackupSnapshot()` both resolved (necessarily async — the snapshot walks every persisted key and writes to IndexedDB). Two changes that both crossed the threshold before that first snapshot finished could each independently call `takeSnapshotAndRotate()`, creating two snapshots for one threshold crossing. Fixed with an in-flight guard (`snapshotInFlight`/`snapshotPending` module state in `autoBackup.ts`): a threshold crossing while a snapshot is already running sets a pending flag instead of starting a second one, and the guard re-checks once the in-flight snapshot finishes. Caught by `autoBackup.test.ts` failing with one extra snapshot than expected; confirmed via temporary logging (removed) that showed two overlapping `takeSnapshotAndRotate()` calls, not a test-harness mismatch.
  - **Two separate test-isolation traps, also fixed, documented in `autoBackup.test.ts`'s header comment**: `vi.resetModules()` between tests means every module touched — `autoBackup.ts`, the stores it subscribes to — must be dynamically re-imported fresh inside each test, not statically at the top of the file (a statically-imported store is a different instance than the one `autoBackup.ts` itself re-imports after reset). And `todo-autobackup-score` in the fake `localStorage` is NOT cleared by `vi.resetModules()` (it only resets the JS module graph, not storage), so a score saved by one test leaked into the next test's `initAutoBackup()` — fixed with an explicit `localStorage.removeItem('todo-autobackup-score')` in `beforeEach`. Also unrelated: `setAutoBackupChangeThreshold` clamps to a minimum of 5, so early drafts of these tests that requested a threshold of 1 or 3 were silently clamped and failed for that reason alone, not a bug — since fixed by using 5 (the minimum) throughout.
